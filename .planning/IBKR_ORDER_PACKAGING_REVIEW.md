# IBKR Order Service Packaging — Node 8.3 Focused Review

## Scope

TREE `8.3` only: standalone operator packaging, secure local caller handoff seam, deterministic permission-independent acceptance, and future integration documentation.

## Implemented boundary

- production `order-service` entrypoint composes the existing `CpgwAdapter` over the existing scoped loopback HTTPS transport;
- process mode defaults to `DRY_RUN`; only explicit `--live` arms the process-level LIVE gate;
- CPGW URL override is HTTPS + loopback only, excludes credentials/query/fragment data, and insecure TLS remains scoped to the dedicated CPGW client;
- caller token remains generated by the existing service runtime, is not printed/persisted, and is available to an approved Node parent only through in-memory IPC;
- Windows launchers are independent from the Market Flow US analysis runtime and use `call npm ...` so exit-code/cleanup control returns to the launcher;
- real CPGW session compatibility check cannot accept `--live`;
- deterministic acceptance uses only `FakeLiveIbkrAdapter`, exercises the real loopback HTTP service + DuckDB idempotency store, and reports `SYNTHETIC_ONLY` / `realOrderSubmitted=false`;
- future integrations are documented to consume the authenticated local API and not bypass the sidecar.

## Static adversarial review

Checked before CI:

1. No account ID, credential, cookie or session material was added to committed config/launcher content.
2. Token value is never written to console/file/report; only the existing runtime return value and optional Node IPC message carry it in memory.
3. `--live` does not bypass request LIVE, provider permission, what-if, SELL guard, reply confirmation or idempotency gates.
4. `--allow-insecure-loopback-tls` remains independent from `--live` and does not set process-global TLS flags.
5. Production binding remains the existing exact `127.0.0.1:8770`; an accidental attempted port override in the initial operator seam was removed before CI and regression-guarded.
6. New Windows CMD files use `call` when invoking `npm.cmd`; an initial missing-`call` defect was fixed before CI and regression-guarded.
7. Acceptance request IDs are unique across scenarios except where replay/reconciliation is intentionally under test.
8. Synthetic acceptance never invokes real CPGW transport and never claims real-money evidence.
9. Existing order-service lifecycle/security implementation is reused rather than duplicated.
10. Fast CI adds the standalone synthetic acceptance after unit/service suites so it does not contend with fixed-port service tests running in parallel.
